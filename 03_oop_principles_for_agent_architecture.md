# Инструкция: принципы ООП при проектировании и аудите структуры агентов

Применяй эти правила при анализе существующей архитектуры и при проектировании изменений. Каждое нарушение, найденное на аудите, — строка в таблицу неэффективностей с доказательством (файл/строка/фрагмент промпта) и severity. Принципы — инструмент упрощения системы, не догма: если применение принципа добавляет слоёв и абстракций, но не убирает дублирование и не упрощает замену компонентов — не применяй.

## 1. Инкапсуляция: агент — это капсула

- Каждый агент объединяет своё состояние (контекст, память, промпт) и операции над ним. Прямой доступ одного агента к внутреннему состоянию другого запрещён.
- У агента есть публичный контракт (вход, выход, поведение при ошибке) и приватная часть (системный промпт, внутренние тулы, промежуточные рассуждения). Извне доступен только контракт.
- На каждой границе агента — валидация входа детерминированным кодом: схема, типы, диапазоны. Не «попроси модель проверить», а код, который отклоняет невалидный вход.
- Конфигурация, которую агент не должен менять в рантайме (ключи, эндпоинты, лимиты), задаётся один раз при инициализации и недоступна для изменения из диалога или контекста.

## 2. Проектируй на уровне интерфейсов

- Прежде чем создавать агента — опиши его интерфейс: имя операции, схема входа, схема выхода, поведение при ошибке. Только потом реализация.
- Оркестратор и соседние агенты зависят от интерфейса, а не от реализации. Им должно быть безразлично, что внутри: LLM, детерминированный код или готовый скилл.
- Замена «LLM → код» не должна трогать остальную систему — меняется только реализация за интерфейсом. Если для замены нужно править соседей — интерфейс спроектирован плохо.
- Обобщённые компоненты (память, хранилище, очередь задач) проектируй как один generic-интерфейс (CRUD с параметром типа), а не отдельный компонент под каждого агента.

## 3. Dependency Injection: зависимости — извне, по интерфейсу

- Агент не должен знать, какая конкретно модель, БД или поисковик за его тулами. Все зависимости передаются при инициализации по интерфейсу.
- Подмена реализации (другая модель, mock для тестов, код вместо LLM, готовый плагин вместо самописного) — через конфигурацию, без правки агента.
- Проверка на аудите: если для замены модели или хранилища нужно править промпт или код агента — нарушение, в таблицу неэффективностей.

## 4. Композиция vs агрегация: определи, чьи это части

- Композиция: субагент, нужный только одному родителю, создаётся родителем, живёт и умирает с ним. Не выноси его в общую инфраструктуру «на всякий случай».
- Агрегация: разделяемые ресурсы (общая память, общий тул, общий MCP-сервер) передаются агентам извне и живут независимо; их используют несколько агентов.
- Для каждой связи «агент — субагент/ресурс» на аудите явно определи тип. Типовые ошибки: разделяемый ресурс, зашитый внутрь одного агента (дублирование); одноразовый субагент в общей инфраструктуре (лишняя сложность).
- Оркестратор делегирует: вызывает субагентов и тулы, а не делает их работу сам.

## 5. Полиморфизм: один вызов — разные исполнители

- Оркестратор вызывает всех исполнителей единообразно, через общий контракт («выполни задачу → верни результат по схеме»), не различая, кто внутри: LLM-агент, скрипт или скилл.
- Антипаттерн: оркестратор с отдельной веткой if/else под каждый тип исполнителя. Нашёл — в таблицу неэффективностей, severity major.
- Пока исполнители взаимозаменяемы за общим контрактом, детерминированная реализация встаёт на место вероятностной незаметно для системы.

## 6. Наследование: применять экономно

- Уместно для конфигураций: базовый шаблон агента (общие правила, формат отчёта, guardrails) → специализации, добавляющие своё.
- Глубокие иерархии (наследник наследника наследника) — сложность, противоречащая цели упрощения. Если специализация сводится к «другой набор тулов + другой контекст» — достаточно композиции и интерфейсов, без иерархии.

## 7. Singleton: общие ресурсы — в одном экземпляре

- Ресурсы, которых должно быть ровно один на систему: подключение к БД, клиент внешнего API с лимитами, общее хранилище памяти, реестр агентов.
- Каждый агент, создающий «своё» подключение к общему ресурсу, — неэффективность: дублирование соединений, рассинхрон состояния.
- Проверка на аудите: найди все точки создания клиентов и подключений (grep по кодовой базе); больше одной точки создания на общий ресурс — в таблицу неэффективностей.

## 8. Слои: решения отдельно от доступа к данным

- Логика принятия решений агента (что делать) не смешивается с механикой доступа (как достать данные, как дёрнуть API). Доступ — в тулы/репозитории за интерфейсами; решения — в агенте.
- Симптом нарушения: в системном промпте агента зашиты детали конкретного хранилища или API. Смена хранилища не должна требовать правки промпта.

## Чеклист аудита

Для каждого компонента и связи ответь:

1. Есть ли у агента явный контракт входа/выхода и валидация входа кодом? Лезет ли кто-то в его внутренности напрямую?
2. Описан ли компонент интерфейсом, или соседи зависят от его реализации?
3. Передаются ли зависимости извне, или зашиты внутрь?
4. Каждая связь — композиция или агрегация? Тип выбран осознанно?
5. Оркестратор вызывает исполнителей полиморфно, или там ветвление под каждый тип?
6. Есть ли неоправданно глубокие иерархии конфигураций?
7. Общие ресурсы — в одном экземпляре, или каждый агент создаёт свои?
8. Разделены ли слои: решения агента vs доступ к данным/тулам?

Каждое «нет» — строка в таблицу неэффективностей с доказательством.
